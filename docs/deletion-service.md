# Composed internal deletion service — 27 October 2026

The service now composes admission/status, durable claiming, archive verification, session revocation, free-only billing, app purge, supported Auth removal and verified completion. Source-only, not deployed: no new private Worker, database credential, role, secret, live migration or enabled public route.

`deletionService({database,auth,archive,issuer,billingMode})` requires the restricted primary autocommit database connection, server-owned Supabase client, archive binding and explicit no_provider_ever_enabled billing mode. `confirm` durably admits the exact confirmed owner and attempts that job immediately while the transient access token is available. Its response means accepted, not necessarily completed. `status` delegates to owner-authenticated status. `runNext()` processes at most one due job, accepts no token or owner selector and is reserved for a trusted scheduler/operator. There is no automatic polling or scheduled deployment here.

Claims are atomic SKIP LOCKED updates with fresh five-minute tokens. Each execution captures its token. Archive/session evidence is written only after observed success with a matching live job/owner/lease; stale updates fail. Admission already blocks application access; blockAccess rechecks that durable barrier. Any stage failure invokes the existing fenced retry function, leaving a one-minute delay and a coarse failure stage. Failure to release a lease reports retryScheduled:false; expiry recovery remains possible. Provider payloads, tokens and owner IDs are not included in execution results.

Archive calls are bounded; Auth adapters have bounded waits. Database connections MUST enforce statement/lock/network timeouts and use autocommit. The service does not provide a database transport/pool or lease renewal. Long executions expire and stay pending; external side effects may outlive timeouts and must be reconciled by the existing idempotent/readback stages. No code fabricates replacement tokens or treats a ban as logout. Background jobs with remaining sessions and no usable token cannot proceed and require the authenticated recovery path.

Verification: three composed PostgreSQL WASM groups exercise real candidate migrations and production modules with synthetic Auth/R2: archive outage preserves app rows and reschedules; provider outage/tokenless retry stays pending; a later confirmed retry runs all stages to completion, removes only A, preserves B/tombstone/archive authority and leaves no runnable job. Provider managed-table mutations exist ONLY in the test fixture as stand-ins for API calls. The fixture includes customers/subscriptions; the separate purge suite covers all six app tables. This is not a live Supabase/R2 end-to-end deletion result.

The native CI workflow now runs admission, free billing, purge/readiness/completion and composition suites alongside its existing PostgreSQL 17/18 concurrency/restore gates. Before activation: private Worker/database wiring and least-privilege privileges, approved actual billing mode, all candidate migrations/advisors, request lifecycle handling, scheduler/recovery, retained backup policy and real disposable-account tests. Do not enable the public flag yet.
