# Owner-authenticated deletion status — 27 October 2026

Candidate implementation; no live feature activation or database change. The existing feature gate now requires both confirm and status RPC methods plus rate limiting. POST /api/account/deletion/status uses the same exact-Origin, bearer, JSON size/deadline and owner-keyed limiter boundary as admission; body must be empty. No owner or job ID selector is accepted from the browser. The response contains only state: none, pending or complete.

The internal status service verifies signed claims against the configured issuer and the current provider identity, then runs a parameterized read against the private jobs and managed Auth tables. It verifies the exact live session belongs to the subject, is not expired, and the user is confirmed/non-anonymous. A deleting/tombstoned account may read its own job status; application data access remains blocked. Provider failures, revoked sessions and malformed responses never become a successful status response. No new client privileges are granted.

The confirmation component includes a status panel outside the workspace, available after acceptance and on blocked-account login. It performs user-initiated checks, not polling. Identity change clears the panel and invalidates in-flight replies. Pending and unavailable wording explicitly does not imply erasure. Completed deletion normally removes the user's Auth identity, so that former user cannot authenticate to this endpoint: unavailable is expected after revocation/deletion and does not prove completion. There is no anonymous receipt endpoint or permanent credential. Final user-visible completion after Auth removal still requires an independently designed receipt/notification or operator channel; this change does not solve that by weakening authentication.

Validation: Node 175/175; PostgreSQL admission/status two groups verify own pending status, another owner's empty result, wrong-owner session denial and revoked-session denial. DOM status tests verify pending wording and discard a stale complete reply after identity clear. Existing bundled boot and workerd smoke regressions are run against rebuilt assets. Tests use synthetic provider responses/tables, not live accounts. No browser visual/a11y audit or production deployment claimed.

Remaining activation work includes the restricted service composition and database role/connection, durable evidence writers, lease renewal, admission recovery, production billing-mode decision and retention/restore completeness. Existing production Wrangler configuration remains disabled.
